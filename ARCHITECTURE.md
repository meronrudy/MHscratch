# Dynamic Hypergraph Engine Architecture

## 1. Overview

This document provides a comprehensive architectural overview of the dynamic hypergraph engine. The project's goal is to create a high-performance engine that can model and simulate complex systems by representing them as a dynamic hypergraph embedded in a dynamic Riemannian manifold.

The engine is designed to be:

*   **Dynamic**: The hypergraph structure and the manifold geometry can change over time.
*   **Performant**: The engine is designed for high performance, using techniques such as parallel execution and SIMD.
*   **Deterministic**: The engine's execution is deterministic, which is crucial for reproducibility and debugging.
*   **Modular**: The engine is composed of several loosely-coupled crates, each with a specific responsibility.

## 2. Architecture

The engine is a Rust workspace composed of several crates. The modular architecture is designed to separate concerns and facilitate parallel development.

```
crates/
  core/         # Core data structures and traits (e.g., IDs, epochs).
  hypergraph/   # Dynamic and frozen hypergraph data structures.
  manifold/     # Manifold, metric, and geometry-related operations.
  bridge/       # Connects the hypergraph and the manifold (gating, caching).
  exec/         # Event-driven execution engine.
  analysis/     # Hypergraph analysis algorithms (e.g., Laplacian).
  verify/       # Determinism verification, hashing, and replay.
```

### Crate Responsibilities

*   `crates/core`: Provides fundamental data structures and traits used throughout the engine, such as custom ID types (`NodeIx`, `EdgeIx`), and the concept of `Epoch` for tracking state changes.

*   `crates/hypergraph`: Implements the core hypergraph data structures. This includes the dynamic hypergraph (`HypergraphDyn`), which can be modified, and the frozen hypergraph (`HypergraphFrozen`), which is an immutable, high-performance representation suitable for execution.

*   `crates/manifold`: Contains the logic for the Riemannian manifold, including the `ManifoldStore` for storing geometric data, metric operations, and geodesic computations. It also includes a spatial index for efficient neighborhood queries.

*   `crates/bridge`: This crate acts as a bridge between the `hypergraph` and `manifold` crates. It is responsible for "gating," which determines which hyperedges are active based on the geometry of the manifold. It also includes caching mechanisms to avoid recomputing expensive geometric queries.

*   `crates/exec`: Implements the event-driven execution engine. It includes an event queue, a scheduler, and the logic for "firing" hyperedges and "applying" their effects to the manifold.

*   `crates/analysis`: Provides tools for analyzing the hypergraph structure, such as computing the hypergraph Laplacian.

*   `crates/verify`: This crate is responsible for ensuring the deterministic execution of the engine. It includes tools for hashing the state of the system, replaying traces, and verifying invariants.

## 3. Data Structures

### `HypergraphDyn`

The `HypergraphDyn` is a dynamic hypergraph data structure that supports adding and removing nodes and edges. It is optimized for efficient modifications.

### `HypergraphFrozen`

The `HypergraphFrozen` is an immutable, high-performance representation of the hypergraph. It is generated by "freezing" a `HypergraphDyn`. The frozen representation is optimized for traversal and is used by the execution engine.

### `ManifoldStore`

The `ManifoldStore` is a data structure that stores the geometric state of the system. It contains the points in the manifold and their velocities. It supports operations such as integration, which updates the state of the manifold over time.

## 4. Core Concepts

### Geometric Gating

Geometric gating is the mechanism by which the geometry of the manifold influences the activity of the hypergraph. Each hyperedge has a "gate" that determines whether it is active or not. The gate is a function of the geometry of the nodes connected by the hyperedge.

### Event-Driven Execution

The engine uses an event-driven execution model. Changes to the system are represented as events, which are placed in an event queue. The scheduler processes events from the queue, which can trigger the "firing" of hyperedges.

### Determinism

Determinism is a critical property of the engine. The execution of the engine is guaranteed to be deterministic, meaning that given the same initial state and the same sequence of events, the engine will always produce the same final state. This is achieved through a combination of techniques, including a deterministic event queue, deterministic application of hyperedge firings, and careful management of floating-point arithmetic.

## Tier 0 — Baseline (locked)

### Deliverables

-   `HypergraphDyn` edge-centric packed tails
-   `delete_edge()` tombstones + `compact_edges()`
-   `freeze(n_nodes)` → CSR frozen
-   `freeze_checked(opts)` → auto n_nodes, compaction, optional densify

### Acceptance criteria

-   Freeze is two-pass and does not allocate inside inner loops
-   Frozen adjacency slices are O(1) to access
-   Deterministic output for same input ordering

## Tier 1 — Structural Correctness & Robustness

### 1) Dense external ID ingestion

-   **Deliverable**: `DenseIdMap<ExtId=u64>`:
    -   `get_or_insert(ext) -> NodeIx`
    -   optional `recycle(NodeIx)` + free-list
    -   `snapshot()` / `restore()` (optional)
-   **Acceptance**:
    -   Can ingest non-dense IDs without any O(N) remap per insert
    -   Stable internal `NodeIx` across incremental updates (when configured)

### 2) Hyperedge arity classes

-   **Deliverable**: Split storage:
    -   `edges_k2`, `edges_k3`, `edges_k4` as fixed-stride tails
    -   `edges_var` remains packed CSR tails
-   **Acceptance**:
    -   Fixed-arity edges have no per-edge tail offsets (computed as `e*k`)
    -   Specialized loops exist for k=2/3/4 in gating + firing

### 3) Edge signature typing

-   **Deliverable**:
    -   `EdgeSignature` stored edge-aligned
    -   `add_edge_checked(signature, tails, head)` enforces:
        -   tail manifolds match node types
        -   head manifold match
-   **Acceptance**:
    -   No runtime signature checks required during execution in frozen state
    -   Mis-typed compositions fail at insertion, not later

### 4) Incremental freeze (delta snapshots)

-   **Deliverable**:
    -   Dirty tracking: `dirty_nodes: BitVec`, `dirty_edges: BitVec`
    -   Frozen base + overlay: `FrozenBase`, `FrozenDelta { added_edges, removed_edges, patched_adjacency }`
    -   Periodic “merge/compaction” policy
-   **Acceptance**:
    -   Small edge updates do not force O(E) rebuild
    -   Correctness matches full-freeze baseline bit-for-bit when merged

---

## Tier 2 — Geometry–Topology Bridging

### 5) Geometric gating cache

-   **Deliverable**:
    -   `GateCache { edge_active: Vec<u8>, edge_weight: Vec<f32>, epoch: Epoch }`
    -   Invalidator keyed by `(manifold_epoch, graph_epoch)`
-   **Acceptance**:
    -   Recomputes only when either epoch changes
    -   Execution path reads `edge_active`/`weight` without calling geometry ops

### 6) Manifold neighborhood acceleration

-   **Deliverable**:
    -   `SpatialIndex` trait: `rebuild(points)`, `radius_query(center, r) -> &[NodeIx]`
    -   One backend first: KD-tree or ball tree
-   **Acceptance**:
    -   Gate evaluation can restrict candidate edges/nodes using index
    -   Index rebuild cost is explicit and amortized

### 7) Hyperedge → geometric footprint

-   **Deliverable**:
    -   Footprint per edge:
        -   v1: `influence_radius: f32` + optional `anchor: NodeIx`
        -   v2: simplex proxy (k points) with cached centroid
-   **Acceptance**:
    -   Gate uses footprint to avoid full geodesic checks when impossible
    -   Stored edge-aligned, no heap allocations

### 8) Time-aware manifold state

-   **Deliverable**:
    -   `ManifoldStore { epoch, t, dt, point, velocity? }`
    -   `integrate(dt)` hook (pluggable integrator)
-   **Acceptance**:
    -   Deterministic integration given same `dt` sequence
    -   Supports “no-velocity” static mode without overhead

---

## Tier 3 — Execution Semantics

### 9) Event queue

-   **Deliverable**:
    -   `Event { time: u64, priority: u32, node: NodeIx, edge: Option<EdgeIx> }`
    -   Deterministic ordering: `(time, priority, node, edge)` total order
    -   Two implementations: FIFO for equal times, Binary heap for mixed times
-   **Acceptance**:
    -   Same input events always produce same processing order
    -   No allocation per push/pop (reserve upfront or slab)

### 10) Hyperedge firing semantics

-   **Deliverable**:
    -   `FireMode::{Push, Pull}`
    -   `eval_edge(edge, tails, head) -> Delta`
    -   Minimal delta type: `Delta::PointUpdate(NodeIx, Tangent)`, `Delta::Constraint(NodeIx, constraint_id, strength)`
-   **Acceptance**:
    -   Firing reads frozen graph + gate cache only
    -   Push mode triggers edges from dirty tails; Pull mode from requested head

### 11) Apply semantics

-   **Deliverable**:
    -   `apply(delta)`: `exp_map` update (or projection), constraint relaxation step
-   **Acceptance**:
    -   `apply` is the only writer to manifold state during execution
    -   Updates advance manifold epoch deterministically

## Tier 4 — Analysis & Learning

### 12) Hypergraph incidence + Laplacian

-   **Deliverable**:
    -   `IncidenceView` over frozen: iterators for `(node, edge, sign/weight)`
    -   Normalized Laplacian builder into sparse CSR
-   **Acceptance**:
    -   Construction is O(total_tails)
    -   Numerical stability tests

### 13) Coupled Laplacians

-   **Deliverable**:
    -   `L_total = α L_hyper + β L_manifold`
    -   `LinearOperator` trait for matrix-free multiplication
    -   One solver: CG or MINRES
-   **Acceptance**:
    -   Operator application is allocation-free and parallelizable
    -   Regression tests on small graphs match explicit-matrix computation

### 14) Differentiable operators (optional)

-   **Deliverable**:
    -   Jacobian hooks at operator boundary
    -   Minimal autodiff compatibility layer
-   **Acceptance**:
    -   Gradients match finite-difference checks on toy cases

## Tier 5 — Explainability & Guarantees

### 15) Trace capture

-   **Deliverable**:
    -   `Trace { fired_edges, visited_nodes, geodesic_calls?, constraints, epochs }`
    -   Configurable verbosity (off by default)
-   **Acceptance**:
    -   Trace overhead is near-zero when disabled
    -   Trace is sufficient to replay and attribute outcomes

### 16) Replay & determinism proofs

-   **Deliverable**:
    -   Snapshot format: manifold points, frozen graph, event log
    -   Replayer that validates hashes each step
-   **Acceptance**:
    -   Replay reproduces final state bit-for-bit
    -   Mismatch yields minimal counterexample

### 17) Invariant enforcement

-   **Deliverable**:
    -   Units/dimensions feature flags
    -   Edge signature enforcement always on
    -   Debug-only “paranoia” checks for CSR bounds
-   **Acceptance**:
    -   In debug: panics at first invariant breach
    -   In release: no runtime tax in hot path

## Tier 6 — Performance Scaling

### 18) Parallel traversal kernels

-   **Deliverable**:
    -   Rayon batch evaluation of independent edges
    -   Node partitioning to reduce contention in `apply`
-   **Acceptance**:
    -   Speedup on multicore without nondeterminism
    -   Deterministic reduction strategy

### 19) SIMD geometry kernels

-   **Deliverable**:
    -   SoA points mandatory in perf mode
    -   Vectorized `dist` and simple `log`/`exp` for chosen manifold families
-   **Acceptance**:
    -   Measurable throughput improvement in microbenchmarks
    -   No change in results beyond floating epsilon

### 20) Accelerators (optional)

-   **Deliverable**:
    -   Trait-based backend for sparse ops and/or geometry kernels
-   **Acceptance**:
    -   Identical semantics across CPU/GPU backends

### Appendix B: Testing Strategy

# Testing Strategy: Causal Behavior and Determinism

## Core Philosophy

**Test causal behavior, not implementations.** Every test should assert what must move, what must not, and why.

## 1. Demo-Style Tests as First-Class Citizens

Small, narratable systems are the primary test unit. These tests answer:

-   Which edges fired?
-   Which nodes moved?
-   Which nodes stayed fixed?
-   What geometry changed?

### Example: Table-Driven Demo Tests

```rust
struct DemoCase {
    name: &'static str,
    points: Vec<Point2>,
    edges: Vec<(&'static [NodeIx], NodeIx)>,
    eps: f32,
    expected_fired: Vec<EdgeIx>,
    expected_positions: Vec<Point2>,
}

fn run_demo(case: &DemoCase) {
    // setup manifold + graph
    // run one step
    // assert fired edges
    // assert final geometry
}
```

## 2. Causality Tests

### A. Non-Firing Guarantees

If a gate condition is false, nothing downstream moves. Run with conditions just outside the threshold.

### B. Minimal Sufficiency Tests

The minimum change needed to fire an edge is enough. This catches accidental hysteresis, stale caches, and floating-point drift.

### C. No Side-Effects Tests

Only the head of a firing edge may change. Critical for parallelism.

## 3. Trace-Based Testing

Assert on the trace shape, not just results, to ensure explanations remain intrinsic.

```rust
assert_eq!(trace.fired_edges, vec![e0, e2]);
assert!(trace.geodesic_calls <= 1);
```

## 4. Freeze Equivalence Tests

-   **Full Freeze Equivalence**: `freeze_checked` on the same dynamic graph produces bit-for-bit identical frozen graphs.
-   **Incremental vs. Full Freeze**: A full freeze and an incremental freeze from the same state produce identical results.

## 5. Geometry–Topology Boundary Tests

-   **Epoch Invalidation**: Changes to the manifold must invalidate the gate cache.
-   **Spatial Index Correctness**: Brute-force neighbor search and spatial index search must return identical sets.

## 6. Determinism Tests

-   **Replay Equivalence**: Replaying a trace from a snapshot must reproduce the final state bit-for-bit.
-   **Seeded Fuzz with Replay**: Generate random small graphs, run execution, save the trace, and assert that replay matches.

## 7. Metamorphic Tests

Check invariants under transformation.

-   **Translation Invariance**: Translate all points, run, translate back. Geometry should match.
-   **Node Renumbering Invariance**: Permute node IDs, run, undo permutation. Results should match.

## 8. Performance Regression Tests

-   **Allocation Guards**: Assert zero allocations in hot paths and bounded allocations during freeze.
-   **Complexity Guards**: Ensure freeze time scales linearly and gating time is proportional to active edges.

## 9. Property Tests (Tier 3+)

Use for CSR integrity, no panics on random valid graphs, and remap correctness. Avoid for geometry or execution semantics, which require narrative tests.

## 10. Test Taxonomy

Organize tests explicitly by their purpose.

```
tests/
  demo/
  causality/
  freeze/
  geometry/
  exec/
```

## The One Rule

**Every bug should be reproducible with ≤ 5 nodes and ≤ 3 edges.** If a bug requires a giant graph, extract the minimal causal core and add it as a demo-style test before fixing it.

### Appendix C: Rust Best Practices

# Rust-Specific Best Practices for a High-Performance Geometric Engine

These are not generic “Rust tips”; they are the things that matter when you build dynamic graph + geometry + execution engines from scratch.

## 1. Memory Layout Pitfalls

-   **Prefer edge-centric SoA over node-centric AoS**: `Vec<Edge>` with `Vec<Vec<Node>>` tails is slow. The chosen packed-tail CSR-style layout is correct.
-   **`Vec::with_capacity` is not initialization**: Do not assume `len == capacity`. Only write via `push` or explicit indexing after `set_len` (unsafe).
-   **Avoid `Box<[T]>` until frozen**: `Vec<T>` is faster for construction. Convert to `Box<[T]>` only for immutability guarantees.

## 2. Borrow Checker Traps

-   **Design around the borrow checker**: Separate read and write phases structurally.

    ```rust
    // Bad pattern
    for e in edges {
        let p = manifold.point_mut(node); // mutable borrow
        let w = gate.weight(&manifold, e); // immutable borrow
    }

    // Good pattern
    // Phase 1: read-only gather
    let deltas = eval_all(&frozen, &manifold);
    // Phase 2: apply mutations
    apply_all(&mut manifold, deltas);
    ```

-   **Interior mutability is a trap**: `RefCell`, `Mutex`, `RwLock` will kill performance. Use them only at system boundaries, never in hot loops.

## 3. Floating-Point Determinism

-   **Parallelism breaks determinism**: Parallel reductions reorder non-associative floating-point sums.
-   **Mitigations**: Use deterministic chunking, fixed traversal order, or accept epsilon-level drift.
-   **Do not rely on `==` for floats**: Use exact bit checks only at defined sync points, otherwise use tolerance-based validation.

## 4. Trait Design Mistakes

-   **Avoid overly generic traits early**: Specialize first. Generalize only when duplication hurts. Monomorphization cost is real.
-   **Beware `dyn Trait` in hot paths**: Trait objects are vtable lookups. Geometry kernels should be monomorphized and inlined.

## 5. `unsafe` is Not Evil — But Quarantine It

-   **Justification**: CSR construction, SIMD kernels, pointer-based iteration.
-   **Rules**: One `unsafe` block per invariant, comment the invariant, and wrap in a safe function.

## 6. Epochs Are Your Best Friend

-   **Always version mutable state**: Use epochs for manifold state, graph topology, gate caches, and event queues.
-   **Why**: Cheap invalidation and replay validation without deep equality checks.

## 7. Logging and Tracing

-   **Never log inside hot loops**: Collect lightweight trace IDs (`EdgeIx`, `NodeIx`) and expand to rich logs after execution if needed.

## 8. A Testing Strategy That Works

-   **Start with golden-file and replay tests**, not property tests. You need determinism first.

## 9. Compilation Time and Ergonomics

-   Keep crate boundaries clean.
-   Avoid giant generic types crossing crate boundaries.
-   Use feature flags (`perf`, `trace`, `units`).

## 10. The Conceptual Trap to Avoid

-   **Do NOT let tensors creep in early**. Keep the core substrate focused on graph + geometry + events. Tensors belong at the analysis or optional learning layer.

## Guiding Rule

**If a design choice makes memory layout, execution order, or invariants less obvious in code, it is probably the wrong choice.**
